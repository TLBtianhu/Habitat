| 项 | 教程 | 我们的约束 |

| Minecraft | **26.3**（2026-09-15） | **26.1**（mineflayer 上限） |

## 3. 对我们架构的三个硬影响

### 影响 1：她写的是**服务端模组**，重启的是**服务器**，不是她的身体

她的身体是无头浏览器 + mineflayer bot，**没有游戏客户端**。所以：

- 客户端模组（新方块贴图、渲染、GUI）在她身上没有落点；
- **服务端模组**才有意义：新方块/物品/配方/机制/规则，她和观众都能在同一个世界里碰到。

这反而让 L3 更便宜：

```
改模组 → 编译 → 一次性实例验证 → 重启 MC 服务器（20~40s）→ bot 自动重连
```

**重启窗口是服务器，不是身体**——舞台照常推流，转场卡都不用给她的浏览器。比原设计（重启客户端 60s）稳得多。

### 影响 2：工具链要按 26.1 重钉，不能照抄 26.3

`gradle.properties` 里至少三处要改：`minecraft_version`、`minecraft_version_range`、`neo_version`。教程的目录结构和构建脚本可以整体沿用。

### 影响 3：Gradle 的网络坑会直接打在我们的自动化上

教程实测：`maven.neoforged.net` 直连超时，必须走代理；但 `piston-meta.mojang.com`、`services.gradle.org` 走同一个代理反而不通。

对策（按优先级）：
1. **预热一次，之后 `--offline` 构建**：依赖进 `~/.gradle/caches`，她的日常构建不需要网络；
2. 预热用一次性脚本 + 代理，产物缓存在宿主机；
3. 若要在沙箱里构建，得另配 JDK 25 与 Gradle 缓存（WSL 目前没有 java）。
