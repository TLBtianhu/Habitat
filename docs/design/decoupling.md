# 解耦：四个角色，不是两台机器

> 2026-10-31 · 从"服务端 vs 渲染端"和"Windows vs WSL"两处不适感出发。
> 结论：**位置（placement）不是角色（role）。** WSL 不是架构的一部分，只是当前的一个放置方式。

---

## 1. 两处不适感，其实是同一个错误

### 不适感 A：服务端 vs 渲染端

我一直在说"服务端和渲染端"，好像它们是一对。但它们不在同一层：

- **MC 服务端** = 世界状态的**裁决者**（真源），它不产生画面；
- **渲染端** = 把状态**投影**成画面的出口，它不做裁决。

把它们并列，会推出一个错觉：*世界必须被画出来才算存在*。实际上世界在服务端就存在，画面只是它的一种投影——**关掉渲染，世界照跑**。

### 不适感 B：Windows vs WSL

我一直在说"宿主和沙箱"，好像它们也是一对。但它们也不在同一层：

- **Windows** = 这台机器的**放置位置**（哪儿有 GPU、哪儿有屏幕）；
- **WSL** = 在同一个 Windows 上**划出的一块隔离区**（一种放置方式）。

WSL 之所以显得必要，是因为它同时干了三件不相干的事：

| 它干的事 | 是否本质 |
|---|---|
| 提供隔离边界（不让她碰宿主） | ✅ 本质 |
| 提供 Linux 工具链（Xvfb、Node、Java、Chrome） | ❌ 便利，换 Docker/VM 一样 |
| 充当"第二台机器"的心智模型 | ❌ **这是混乱源** |

第三件最要命：它让我们用"两台电脑"去想问题，于是把"角色"和"位置"焊在了一起。

**同一个错误：把在哪做，当成了做什么。**

---

## 2. 正确的分解：四个角色

```
        ┌──────────────┐  命令/策略（少量、可审计）
        │  Authority   │ ─────────────────────────────┐
        │  真源/裁决    │                              ▼
        └──────────────┘                     ┌──────────────┐
               ▲                             │   Worker     │
               │ 遥测/审计                    │  执行/身体    │
               │                             └──────┬───────┘
               │                                    │ 状态增量（单向）
        ┌──────┴───────┐                     ┌──────▼───────┐
        │   Outlet     │ ◄──── 帧/音频 ───── │  Renderer    │
        │  发布/推流    │                     │  投影/出口    │
        └──────────────┘                     └──────────────┘
```

| 角色 | 定义（本质） | 当前放置 | 可否搬走 |
|---|---|---|---|
| **Authority 真源** | 状态在这里被裁决：MC 世界、她的记忆/承诺、凭证、节目单 | 宿主（世界在 WSL 里跑，但那是"服务端进程"，属于真源层） | 可（搬到云） |
| **Worker 执行** | 不可信动作在这里发生：浏览器、bot、她写的代码 | WSL | **可换**（Docker/VM/另一台机） |
| **Renderer 投影** | 把状态变成帧与声音 | 宿主 GPU | 可（另一台机/云渲染） |
| **Outlet 出口** | 编码、推流、录制 | 宿主 ffmpeg | 可 |

**关键不变量**（与位置无关）：

1. **Authority 与 Worker 不得同域**——她崩了不能带走世界；她也不能直接改真源。
2. **Worker 到 Renderer 只能单向出站**——状态出去，画面不回来；反过来只有策略通道。
3. **Renderer 不持有真源**——它只有快照，丢了能重建。
4. **Outlet 必须独立于 Worker**——她崩了直播不断。

只要这四条成立，**放在哪都无所谓**。

## 3. 沙箱 = 能力清单，不是 WSL

这是最尖锐的一点：**我们之前用 WSL 当沙箱，但 WSL 默认并不满足我们的清单。**

它默认把 `C:\` 挂到 `/mnt/c`、默认 `wsl -u root` 免密——两条都违反"Worker 不能碰宿主"。我们是用 `InaccessiblePaths` 手工关掉的。

这说明：**"沙箱"不是一个软件，是一份能力清单；WSL 只是恰好能满足（经过修补）的一个实现。**

清单（v0.1，任何 runtime 必须满足）：

```yaml
sandbox:
  filesystem:
    host_visible: false        # 看不到宿主用户目录
    own_scratch: read-write    # 自己的临时区
    credentials: none          # 里面 grep 不到任何 key
  network:
    egress_allow: [world-server, package-mirror, docs]
    ingress: none              # 不允许外部连进来
  input:
    host_input: none           # 不注入宿主鼠标键盘、不读屏幕
  output:
    state_channel: outbound-only
  process:
    cannot_touch: [renderer, outlet, authority]
```

**WSL 只是 `runtime: wsl` 的一个实现。** 换成 Docker、Firecracker、另一台机器，清单不变。

### 推论：代码里不许出现 "wsl"

现在我们的身体是 `body.py` 跑在 WSL 里、桥在宿主——但**桥不该知道对端是 WSL**。它应该只知道"有一个 Worker 端点，通过一条出站链路连进来了"。

```ts
interface WorkerProvider {
  id: 'wsl' | 'docker' | 'vm' | 'ssh';
  ensure(): Promise<void>;           // 确保 worker 在跑
  capabilities(): SandboxCapabilities; // 返回上面那份清单的实际值
}
```

`bridge.mjs` 只跟"连进来的 worker"说话；`wsl.exe` 只出现在 `providers/wsl.ts` 里。

## 4. 为什么"MC 服务端"属于 Authority 而不是"另一端"

它裁决世界：谁在哪、方块变没变、谁掉血。它是**世界的真源**。

- 她（Worker）连它是**客户端**，只能发意图；
- 它崩了，世界暂停但存档还在；她崩了，世界照跑，她重连后对账（SPEC-03 P-25）；
- 渲染器读的是**她看到的那个投影**，不是世界本身。

所以正确的句子是：

> **Authority 决定"世界是什么"，Worker 决定"她做了什么"，Renderer 决定"观众看见什么"，Outlet 决定"发到哪"。**

四句话，四个角色，互不替代。

---

## 5. 这一改对我们代码的影响

| 现在 | 应该 |
|---|---|
| `body.py` 里写死 `~/opt/chrome`、`systemctl` 假设 | 入口参数化，provider 注入 |
| `bridge.mjs` 只知道"有人连进来" | 补 `hello.capabilities`，桥据此校验清单是否满足 |
| 启动脚本 `wsl -d Ubuntu ...` 散落各处 | 收进 `providers/wsl`，其它模块只调 `ensure()` |
| 文档里"宿主/WSL"混用 | 统一改成"出口/Worker/真源"三种说法 |

**一个验收测试**：把 Worker 从 WSL 换成 Docker（或另一台机器），**舞台、桥、渲染器一行不用改**，只换 provider 配置。做不到，就说明还有耦合。

---

## 6. 一句话

> **WSL 不是概念，"隔离且只能单向出站的一侧"才是概念。**
> 我们真正需要的是那条边界和那条链路；WSL 只是今天恰好能用的一块地。
