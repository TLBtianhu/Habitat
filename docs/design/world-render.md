# 世界视图的正确架构：照抄 Minecraft 自己的分法

> 2026-10-31 · 起因：prismarine-viewer 在沙箱里只有 2–6 fps。
> 结论：**沙箱里不该有渲染器。** 把渲染搬到出口，是世界状态跨边界，不是画面跨边界。

---

## 1. 先回答：MC 的"服务端"到底是什么

一句话：**服务端是一台权威模拟器 + 一个状态广播器，它从不渲染。**

### 1.1 一个 tick 里发生什么

Minecraft 服务端是一个 Java 进程，跑在固定节拍上：**20 TPS = 每 50 ms 一个 tick**。

```
每个 tick：
  收网络包（玩家移动、挖方块、用物品、聊天）
  → 校验（权限、距离、冷却、反作弊）
  → 跑世界逻辑（实体 AI、方块更新、红石、作物、天气、生物生成）
  → 把"变化"打包成增量包，广播给附近玩家
```

关键点：**服务端没有"画面"这个概念**。它只有方块数组、实体表、玩家表。

### 1.2 世界按区块（chunk）组织

- 世界被切成 **16×16×384 的列**（1.18 后高度 384）；
- 只有玩家附近的区块被加载（load）进内存，远处卸载；
- 每个区块是一组 **palette + 位压缩** 的方块 ID 数组；
- 生成区块有独立线程池（1.18 后 chunk gen / IO 并行），但**逻辑 tick 仍是单主线程**——这就是"服务端只吃单核"的由来。

### 1.3 客户端负责三件事，服务端一件都不做

| 职责 | 在哪 |
|---|---|
| 模拟与裁决（谁在哪儿、方块变没变） | **服务端** |
| 把变化编码成包（区块数据、实体位移、方块更新） | 服务端 |
| **把包解成几何、贴图、光照、动画** | **客户端** |
| 本地预测（按键立刻动，不等服务器） | 客户端 |
| 插值与回滚（位置平滑、纠正） | 客户端 |

**客户端发的是"意图"**（我往这边走了、我要挖这个方块），**服务端回的是"事实"**（你现在在这、这个方块没了）。

### 1.4 协议本身

- 二进制包，protodef 描述，varint 长度前缀，zlib 压缩；
- 登录后走 AES 加密（`online-mode=false` 时跳过）；
- 区块数据是**大块推送**，实体是**高频小增量**；
- 这就是为什么"低配机器能玩"：服务端只发数据，几何与像素是客户端自己算的。

## 2. 我犯的错：把渲染器放进了沙箱

原来的链路：

```
WSL: mineflayer(bot) + prismarine-viewer(express/socket.io) + Chrome(WebGL 软件渲染)
                                                              ↑ 2–6 fps，卡死
宿主: 收帧（grab 这个浏览器）
```

这违反了三条已经立过的律：

| 律 | 违反点 |
|---|---|
| **A1 声明唯一真源，光栅化是出口**（[READING](C:\Habitat\READING.md)） | 我把"世界状态"光栅化成像素，再在沙箱里又渲染一次 |
| **B3 勤快只在出口**（同上） | 沙箱本该只出**事件/状态**，结果它在出**像素** |
| **C1 崩溃域不共享** | 渲染把 CDP 堵死，连 `Runtime.evaluate` 都超时 |

更根本的是：**MC 自己都把渲染放在客户端，我却把"客户端"塞进了本该只做协议的那一侧。**

---

## 3. 正确架构：沙箱是"无头客户端"，渲染在出口

```
┌─ WSL（沙箱）────────────────────────┐        ┌─ 宿主（有 GPU）──────────────┐
│ mineflayer bot                      │        │ WorldRenderer                │
│  = 一个 MC 客户端，但"无头"          │  TCP   │  three.js / canvas2d         │
│  只做：连服、收包、维护世界镜像       │ ─────► │  吃 WorldView 增量，自己渲染  │
│  只发：WorldView 增量（~10 KB/s）    │ 出站   │  交给舞台当 WORLD 场景        │
│  不渲染、不开浏览器、不 WebGL         │        │  （GPU 空闲或满载由它决定）    │
└─────────────────────────────────────┘        └──────────────────────────────┘
```

**边界上流动的是"世界状态"，不是"画面"。** 于是：

- 沙箱不需要 GPU、不需要浏览器、不需要 socket.io、不需要 node-canvas；
- 宿主可以自由换渲染器（2.5D、3D、小地图、甚至纯文本面板）；
- 断线重连时，"画面"是重建出来的，不是录出来的——与 A3「一棵声明，三种出口」一致。

## 4. WorldView 协议（我们自己定，v0.1）

10 Hz 推送，只发"她周围看得见的东西"，全部是**声明**，不含任何绘制指令。

```jsonc
{
  "t": "world",
  "seq": 1234,
  "tick": 9876,
  "bot": { "pos": [x,y,z], "yaw": 1.57, "pitch": -0.2, "health": 20, "food": 18 },
  "radius": 24,                      // 覆盖半径（方块）
  "heightmap": { "size": 48, "min": 60, "max": [ /* 48×48 uint8 相对高度 */ ] },
  "blocks": [ [x,y,z,"minecraft:oak_log"], ... ],   // 只在变化时发
  "entities": [ { "id": 7, "type": "zombie", "pos": [...], "yaw": 0 }, ... ],
  "events": [ { "kind": "block_break", "pos": [...] } ]
}
```

- **不做全量区块序列化**：我们不需要 16×16×384 的完整体素，只需要"镜头看得见的一层"；
- **高度图 + 变化列表** 约 10 KB/s 量级，环路完全吃得下；
- 渲染器拿它去画：高度图当骨架，变化列表当细节，实体当点缀。

## 5. 两个渲染后端（可热换）

> **2026-10-31 修正**：俯视图是**给模型**的，不是给观众的。观众要的是**她的第一视角**。
> 两者共用同一份世界状态，但相机、精度、预算完全不同。

| 档 | 相机 | 精度 | 给谁 | 实现 |
|---|---|---|---|---|
| `present` | **第一人称**，贴在她眼睛上 | 高（贴图、雾、昼夜） | 观众 | 宿主 GPU：prismarine-viewer `firstPerson` 或 three.js 自绘 |
| `perceive` | 俯视/正交感 | 低（高度图 + 名字） | 模型 | canvas 2D 或纯符号 |

**为什么观众用第一人称**：观众不是在看地图，是在看"她在玩"。俯视图适合判断（有没有路、僵尸在哪），不适合陪看。

**为什么模型不用第一人称**：单帧第一视角信息密度极低（一堵墙挡住就是全绿），而俯视/符号能把"周围 8 格有什么"压成几行字。

### 5.1 第一视角怎么来（关键约束）

第一人称必须**在她眼睛的位置**渲染。三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 宿主相机 bot**（推荐） | 宿主再开一个 mineflayer bot 当"摄像机"，位置同步她的姿态，跑 prismarine-viewer `firstPerson`，宿主 GPU 渲染 | 多一个客户端连接；需同步姿态 |
| B 自绘 three.js | 宿主用世界快照 + three.js 自己搭体素场景 | 要自己做贴图/光照/雾 |
| C 沙箱里渲染 | 在 WSL 里跑 viewer | ❌ 已证伪：软件 WebGL 2–6 fps |

方案 A 的要点：相机 bot 连的是**同一个世界服务端**，它的位置每 tick 被她覆盖（`physicsEnabled = false`），所以镜头永远在她眼睛上。

### 5.2 这要求一件事：**世界服务端必须在宿主侧**

如果服务端还在 WSL 里，宿主的相机 bot 连不进去（host→WSL 不通）。
把服务端搬到宿主后：

- 宿主相机 bot ↔ 服务端：本地回环，通；
- WSL 的她 ↔ 服务端：出站到宿主，通（已验证 WSL→宿主 127.0.0.1 可达）；
- 顺带把 **V1（世界与 Worker 同域）** 一起修掉：世界真源离开沙箱。

**结论：这一步同时解决"第一视角"和"Authority 与 Worker 同域"两个问题。**

---

## 6. 这一改删掉了什么

| 删掉 | 原因 |
|---|---|
| 沙箱里的 prismarine-viewer 服务端 | 渲染不需要在沙箱 |
| socket.io / express | 同一件事 |
| 沙箱 Chrome 的 WebGL | 不再需要 |
| `node-canvas`（946 MB 里的一大块） | 只为 viewer 服务端准备 |
| host→WSL 的端口访问 | 世界数据走已经通的反向链路 |

**净效果**：沙箱变轻（只跑 bot），宿主用真 GPU，世界视图从"2 fps 卡死"变成"30–60 fps 的投影"。

---

## 7. 代价与后续

- 我们自己要写一个**世界镜像**（读 bot 的 `bot.world` / `bot.entities`）和一个**渲染器**；
- 3D 精度不如真客户端（没有光影、没有动画模型）；
- 若将来要"接近真 MC"的观感 → 走 v2 的 remote-bot 桩，复用 prismarine-viewer 的渲染器，但**渲染仍在宿主**。

## 8. 一句话

> **Minecraft 把"模拟"留在服务端、把"渲染"放在客户端；我们也该把"模拟"留在沙箱、把"渲染"放在出口。**
> 之前 2 fps 不是性能问题，是位置放错了。
